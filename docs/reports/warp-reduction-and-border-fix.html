1. 測り方

1.1 交絡を断つ: 1 本のソースに 2 つのフラグ

cand_ecc.cpp（境界修正）と fast_ecc.cpp（warp 削減）は別々の upstream スナップショットから 派生しているので、そのまま突き合わせると差分に無関係な要因が混ざる。 eval/uni_ecc.cpp は 1 つの本体に 2 つの真偽フラグを持たせ、4 通りを同じコードパスから出す。

既存実装との一致を確認済み。eval fixedpoint est=cv,ubase,cand,ufix,fast,ufast motion=affine で ubase=cv、ufix=cand、ufast=fast が cornMed / バイアス / rho すべて小数 4 桁まで一致する。

境界修正は上流 PR と同じ形（ループ外で templtMask のリングを落とし、ループ内で bitwise_and + マスク外の勾配をゼロ化）にした。研究用の cand_ecc.cpp は 毎反復リングを作り直しており、そのままだと速度比較に余分なコストが乗る。

1.2 速度は反復数を固定して測る

ms 列は 1 回の呼び出しの実時間なので、収束までの反復回数が推定器ごとに違うと 1 反復あたりのコストが見えない。eps=0 を渡すと打ち切り判定 |ρ−ρ′| ≥ 0 が常に成立し、 どの推定器も iters 回ぴったり回る。これを「1 反復コスト」とし、 既定の eps=1e-6 で収束まで回したものを「実時間」として別に測った。

各セル 3 反復の中央値。順序効果は窓 256 で順序を入れ替えて確認した（無し）。 1 回だけの測定では 48% の偽の差が出たので、反復は必須。

速度の数値はマシンが静かな状態で取り直したものである。最初の測定は同じマシンで別の重い処理が 走っていて汚染されており、絶対値が 1.4〜1.6 倍膨らんでいた（affine 窓 512 の 1 反復コスト: 汚染 178 ms → 再測定 129 ms）。比の傾向は変わらなかったが、個々のセルは最大 0.14 動いた （収束実時間の translation 窓 256 で 1.59× → 1.45×、1 反復コストの affine 窓 128 で 1.16× → 1.27×）。 再測定では各反復の前後で CPU 負荷を記録しており（C1b/C2b の @@@@ 行）、 0〜35% の範囲に収まっている。

1.3 並列化

窓 200 px の ECC は 1 プロセスがほぼ 1 コアしか使わない。12 コア機で逐次バッチを 2 本流すと 17% しか回らないので、精度系は設定ごとに 1 プロセスへ分けて 17 並列で流した。 速度測定だけは単独で実行。

これは窓 200 px での話である。§2.5 のとおり warpAffine は窓 384 px 以上でスレッドプールに乗るので、 大窓では ECC も複数コアを使う。スレッド数を固定したいときは threads=N を使うこと — OPENCV_FOR_THREADS_NUM はこのビルドでは無視される。

共通条件: analytic シーン（真値が厳密）、window=200、margin=8、gaussFiltSize=5、trials=200〜300、seed=12345。

2.5 原因: OpenCV のスレッド化の非対称性（特定済み）

訂正。本稿の初版はここで「スレッド化ではない、メモリ帯域が有力」と書いた。 あの対照は OPENCV_FOR_THREADS_NUM=1 を使ったが、この OpenCV ビルドはこの環境変数を無視する （cv::setNumThreads を直接呼んで判明。環境変数を付けても getNumThreads() は 12 のまま）。 つまり多スレッド同士を比べており、対照になっていなかった。結論は逆である。

eval に threads=N（cv::setNumThreads を呼ぶ）を追加して測り直した。 affine、trials=12、3 反復の中央値:

threads=4 列は後日 affine で測り直したもの（1 反復コスト、3 反復の最小値）。 4 スレッドを常用の動作点とする——このマシンは 6C/12T だが 12 並列は実利用の想定から外れる。 中間の挙動を示し、窓 512 以上で利得が落ちる傾向は 12 スレッドと同じ。

単スレッドなら、warp 削減の効果は窓 128 から 768 まで 1.27〜1.31× で完全に平坦。 劣化はスレッドプールを使ったときにしか起きない。

2.6 含意: 大窓では warp はもう主要コストではない

この機序には続きがある。窓 768・12 スレッドでは、1 反復 16.2 ms のうち削れる warp 2 回は わずか 1.12 ms（7%）でしかない。仮に足す側を完璧に融合・並列化しても、上限は 1.06× 前後にとどまる。

大窓での改善余地は勾配経路にはもう無い。残り 9 割を占めるのはガウス・ニュートンの代数 （ヤコビアン構築と project_onto_jacobian_ECC、homography では 8 プレーン）である。 単スレッドでは逆に warp が 1 反復の 18% を占めるので、warp 削減がそのまま効く。
後日追記: この予測は実装して確認できた。ガウス・ニュートン段を融合すると、その余地は実際に取れる （ECC_gauss_newton_fusion.html）。4 スレッド・窓 768 で融合 GN 単独が translation 1.27× / euclidean 1.88× / affine 2.00× / homography 2.47×。 warp 削減が無力になる領域とちょうど相補的である。

実用上の読み替え:

  • cv::setNumThreads(1) で使う場合（組み込み、あるいは外側で並列化している場合）、 warp 削減はどの画像サイズでも 1.27〜1.31× 効く。
  • スレッドプールを使い、かつ窓が 384 px を超える場合、warp 削減の価値はほぼ無い。 害もない（break-even）が、期待もできない。この領域は融合 GN が埋める。
  • 窓 384 px 以下なら、スレッド数によらず 1.25〜1.5× 効く。
  • 常用の動作点を 4 スレッドとすると、warp 削減は窓 256 で 1.26〜1.52×、 窓 768 で 1.04〜1.17×。12 スレッドほど極端には落ちない。

前段ぼかしは耐雑音性を買っていない。σ=10 で gauss=3 がわずかに最良である以外、 どの雑音水準でも「ぼかさないほうが正確」。ECC はすでに 4 万画素で平均しており、 ぼかしは情報を増やさずに位置決めの手がかり（勾配エネルギー）を削るだけ、と読める。

したがって gaussFiltSize の存在意義は収束半径に一本化される。 既定値を動かすなら、その根拠は §3.2 だけであって「ノイズに強くなるから」ではない。

4. まとめと次の一手

確定したこと

  1. warp 削減は境界修正の上にそのまま乗る。精度・収束半径ともに劣化ゼロ、窓 128〜256 px で 1.24〜1.49× 速い。fast-ecc 単体に残っていたスケールバイアスは組み合わせると消えるので、精度でも組み合わせが最良。
  2. fast-ecc 単体の精度優位は gaussFiltSize=5 に依存した偶然だった（§2.1.1）。 マスクを 1 px 削っているだけなので、リングが 1 px（gauss=3）のときだけ過不足なく覆われる。 gauss=9 では残留バイアス −1.8e−04 (t=−75)、gauss=17 では −7.4e−04 (t=−51) まで戻る。
  3. 窓 384 px を超えると高速化が消える（768〜1024 px で 0.98〜1.03×、実質 break-even）。 はっきり遅くはならない。
  4. 原因は OpenCV のスレッド化の非対称性で特定済み（§2.5）。warpAffine は窓 384 px 以上で スレッドプールに乗り（4.5× まで）、filter2D/addWeighted は最後まで乗らない。 単スレッドでは節約が画素数に厳密比例（dt/Mpx が 64 倍の画素数変化に対して 6.8〜7.5）し、 比も 128〜768 px で 1.27〜1.31× と平坦。なお本稿初版はここを「スレッド化ではない」と誤って結論した — 対照に使った OPENCV_FOR_THREADS_NUM をこのビルドが無視していたため。
  5. 大窓では warp はもう主要コストではない。窓 768・12 スレッドでは 1 反復 16.2 ms のうち 削れる warp は 1.12 ms（7%）。足す側を完璧に融合・並列化しても上限は 1.06× 前後で、 残り 9 割はガウス・ニュートンの代数にある。
  6. 境界修正自体は速度中立。上流 PR に性能面の懸念はない。
  7. gaussFiltSize の最適値は 5 → 9 に動く（精度同じ、収束率 +4 点）。修正前は 5 が上限に近い妥協点だった。
  8. 前段ぼかしは耐雑音性を買っていない。買っているのは収束半径だけ。

手をつけていないこと

  • 大窓の改善はガウス・ニュートン代数側にある（§2.6）。勾配経路を融合・並列化しても 窓 768・12 スレッドでの上限は 1.06× 前後。手を入れるなら project_onto_jacobian_ECC の方。
  • 足す側の融合カーネル。filter2D × 2 + addWeighted × 2 + setTo を parallel_for_ ベースの 1 パス（10 プレーンの読み書き → 3 プレーン）に畳めば、 少なくとも 384〜768 px の谷は浅くできる。単スレッド利用者には効かない（そこはすでに 1.27×）。
  • gaussFiltSize 既定値変更の上流提案。§3.2 は根拠になるが、既定値の変更は既存利用者の挙動を変える。 #29775 がマージされるまでは持ち出さないほうがよい。
  • 小窓＋大 gauss の残留バイアス（+4.9e−05, t=4.0）。符号が逆で機序が違う。
  • 実画像（synth=resample）での再現。本稿は全て analytic シーン。 真値が厳密という利点と引き換えに帯域が単調（freq=0.22 の 40 成分）。

再現方法

# ビルド
cd eval
cmake -S . -B build -DOpenCV_DIR=C:/opencv/build/x64/vc15/lib
cmake --build build --config Release

# 精度・バイアス
./build/Release/eval fixedpoint est=ubase,ufix,ufast,uboth motion=affine trials=300
# 収束半径
./build/Release/eval basin      est=ubase,ufix,ufast,uboth motion=affine trials=200
# 1 反復コスト（eps=0 で反復数を固定）
./build/Release/eval accuracy   est=ubase,ufix,ufast,uboth motion=affine window=256 iters=20 eps=0 trials=30
# gauss スイープ
for g in 1 3 5 7 9 13 17 21 31; do
  ./build/Release/eval fixedpoint est=ubase,ufix,uboth motion=affine gauss=$g trials=300
done

# スレッド化の対照（threads= は cv::setNumThreads を呼ぶ。
# OPENCV_FOR_THREADS_NUM はこのビルドでは効かないので使わないこと）
for th in 1 12; do
  ./build/Release/eval accuracy est=ufix,uboth motion=affine window=768 \
      threads=$th iters=20 eps=0 trials=12
done

# 演算単位の内訳（-tN でスレッド数を固定）
./build/Release/opbench -t1  128 192 256 384 512 768 1024
./build/Release/opbench -t12 128 192 256 384 512 768 1024
