1.1 記号

記号意味

1.2 反復が解く式

ECC（Evangelidis & Psarakis, PAMI 2008）は正規化相関を最大化する。

ρ(p) = ⟨ t‾ , i‾(p) ⟩ ‖t‾‖ ‖i‾(p)‖

前進加算型のガウス・ニュートン反復で、各ステップはまず次の 3 つを作る。

H= GTG vi= GTi‾ vt= GTt‾ H は P×P のヘッセ行列（グラム行列）。 vi, vt は長さ P のベクトル。

照明変化を吸収するスケール λ を求め、

λ= ‖i‾‖2 − viT H−1 vi ⟨t‾, i‾⟩ − vtT H−1 vi

パラメータ更新を得る。

Δp= H−1 GT ( λt‾ − i‾ )
ここで GT を掛ける操作が 4 回ある — H で 1 回（自分自身と）、vi と vt で 1 回ずつ、そして Δp で 1 回。 OpenCV はこれを project_onto_jacobian_ECC() の 4 回の呼び出しで実装している。 本稿はこの 4 回を 0 回にする。

2. 現状の実装とそのコスト

2.1 ヤコビアンのレイアウト

OpenCV はヤコビアンを hs × (ws*P) の 1 枚の Mat として持つ。 P 個の「ブロック」が横に並んだ形である。

// modules/video/src/ecc.cpp
static void image_jacobian_affine_ECC(const Mat& src1, const Mat& src2,
                                      const Mat& src3, const Mat& src4, Mat& dst)
{
    const int w = src1.cols;
    dst.colRange(0, w)     = src1.mul(src3);  // gx * x
    dst.colRange(w, 2*w)   = src2.mul(src3);  // gy * x
    dst.colRange(2*w, 3*w) = src1.mul(src4);  // gx * y
    dst.colRange(3*w, 4*w) = src2.mul(src4);  // gy * y
    src1.copyTo(dst.colRange(4*w, 5*w));        // gx
    src2.copyTo(dst.colRange(5*w, 6*w));        // gy
}

この横並びレイアウトのせいで、各ブロックは連続メモリではなく、行ストライドが ws*P の飛び飛びのビューになる。

3. 最適化 1: 4 番目の射影は数式から消える

更新の射影を展開するだけでよい。

GT ( λt‾ −i‾ ) = λ (GT t‾) − (GT i‾) = λvt −vi 線形性そのもの。vt と vi はすでに計算してある。

4 回目の project_onto_jacobian_ECC（12 面）も、その入力である error 行列の生成（3 面）も要らない。85 → 70 面。

// before
error = lambda*templateZM - imageWarped;
project_onto_jacobian_ECC(jacobian, error, errorProjection);

// after
errorProjection = lambda*templateProjection - imageProjection;
これは構造を一切変えない 3 行の置き換えで、レイアウトにもアルゴリズムにも触れない。 精度も変わらない（浮動小数の丸めは変わるが、中間の error 行列を経ないぶん誤差要因はむしろ減る）。 単独で上流に提出でき、しかも全動作種別に効く。

4. 最適化 2: affine のヘッセ行列は 18 自由度しかない

4.1 ヤコビアンは面分割積である

affine warp は

x′= p0x+ p2y+ p4 y′= p1x+ p3y+ p5

なので、画素 n における 6 本の偏微分は次のようになる。

∂i‾ ∂p = [ gxx gyx gxy gyy gx gy ] 左から p0 … p5 に対応。 末尾 2 本は平行移動なので座標が掛からない（= 1 が掛かる）。

これは 2 要素ベクトル gn と 3 要素ベクトル cn のクロネッカー積にほかならない。

G の第 n 行 = gn ⊗ cn , gn= (gx,gy) , cn= (x,y,1) 6 = 2 × 3。G は勾配行列と座標行列の面分割積（行ごとのクロネッカー積）である。

したがってヘッセ行列は次の形になる。

H= GTG = ∑n (gn gnT) ⊗ (cn cnT) (a⊗b)(a⊗b)T =(aaT)⊗(bbT) を各画素に適用して和を取っただけ。

gngnT は 2×2 対称で独立成分 3 個 （gx2, gxgy, gy2)、 cncnT は 3×3 対称で独立成分 6 個 （x2, xy, y2, x, y, 1）。よって:

6×6 ヘッセ行列の上三角 21 成分は、3 × 6 = 18 個の和だけで書ける。 残り 3 個は重複である（H12 = H03、 H14 = H05、 H34 = H25 — いずれも gxgy 側の重複）。 affine の ECC ヘッセ行列は一般の対称行列ではない。

4.2 対応表

行が gngnT の 3 成分、 列が cncnT の 6 成分。 セルがヘッセ行列のどの成分になるかを示す。

x2 xy y2 x y 1
gx2 H₀₀H₀₂H₂₂H₀₄H₂₄H₄₄
gxgy H₀₁H₀₃ = H₁₂H₂₃H₀₅ = H₁₄H₂₅ = H₃₄H₄₅
gy2 H₁₁H₁₃H₃₃H₁₅H₃₅H₅₅

射影のほうも同じ構造で、GTv の 第 (g,c) 成分は ∑ngcv。 重複は無く 6 個ずつ、2 本で 12 個。 合計 30 個のスカラを累積すれば、この段はすべて終わる。

4.3 四つの運動種別すべてが同じ形をしている

この構造は affine 固有ではない。ECC のヤコビアンは、どの運動種別でも 「勾配側のベクトル u と座標側のベクトル w の 面分割積のうち、いくつかの列を取り出したもの」として書ける。違うのは u と w の中身と、取り出す列だけである。

運動種別P u（勾配側）w（座標側） 列H の成分数累積するスカラ
translation2 (gx,gy) (1) 2 = 2×1（全部）33
euclidean3 (gr,gx,gy) (1) 3 = 3×1（全部）66
affine6 (gx,gy) (x,y,1) 6 = 2×3（全部）2118
homography8 (gx,gy,gp) (x,y,1) 8 = 3×3 − 13636

累積するスカラの数は必ず tri(K)·tri(L) （tri(n)=n(n+1)/2）になる。 affine だけが 18 < 21 と真に得をしているのは、6 = 2×3 が K,L>1 でかつ 列を全部使う唯一のケースだからである。他は過不足なく一致する。

ただし本当の利得は成分数の削減ではなく、ヤコビアンを実体化しないことにある。 それは P によらず 1 パスで済むので、節約は P とともに増える。§6 の実測はまさにその通りになる （窓 768・4 スレッドで translation 1.27× → homography 2.47×）。

homography の gp は何か

射影 warp のヤコビアンには画素ごとの除算 d=h6x+ h7y+1 が入る。 一見これで面分割積の形が壊れそうに見えるが、壊れない。除算を勾配側に畳み込めばよい。 OpenCV の image_jacobian_homo_ECC は実際そうしている:

gx=Ix/d , gy=Iy/d , gp= −x′gx −y′gy x′,y′ は射影後の座標。hatX_ / hatY_ がこれにあたる。

この 3 本を (x,y,1) に掛けた 9 通りのうち gp·1 を除く 8 通りが、 そのまま 8 本の列である。homography は例外どころか、最も伸びしろの大きいケースだった。

5. 最適化 3: ヤコビアンを作らず、1 パスで、並列に

30 個のスカラを作るのに必要な入力は gx, gy, x, y, ī, t̄ の 6 面だけ。ヤコビアンを書き出す必要も、読み直す必要もない。

データフローの比較（1 反復）

左: 現状。ヤコビアンを実体化し、4 回の射影で読み直す。右: 融合。6 面を 1 回読むだけ。

5.1 内側ループ

行ごとに float で累積し、行末で double に昇格する。 straight-line なのでコンパイラがベクトル化でき、行末の昇格で精度も保てる。

for (int x = 0; x < w; ++x) {
    const float a = pgx[x], b = pgy[x], u = pX[x], v = pY[x];
    const float aa = a*a, ab = a*b, bb = b*b;   // g gᵀ の 3 成分
    const float uu = u*u, uv = u*v, vv = v*v;   // c cᵀ の 6 成分（u, v, 1 は自明）

    g00 += aa*uu;  g01 += aa*uv;  g02 += aa*vv;   // gx² 行
    g03 += aa*u;   g04 += aa*v;   g05 += aa;
    g10 += ab*uu;  g11 += ab*uv;  g12 += ab*vv;   // gxgy 行
    g13 += ab*u;   g14 += ab*v;   g15 += ab;
    g20 += bb*uu;  g21 += bb*uv;  g22 += bb*vv;   // gy² 行
    g23 += bb*u;   g24 += bb*v;   g25 += bb;

    const float ii = pim[x], tt = ptm[x];
    const float ai = a*ii, bi = b*ii, at = a*tt, bt = b*tt;
    pi0 += ai*u; pi1 += bi*u; pi2 += ai*v; pi3 += bi*v; pi4 += ai; pi5 += bi;
    pt0 += at*u; pt1 += bt*u; pt2 += at*v; pt3 += bt*v; pt4 += at; pt5 += bt;
}

1 画素あたり 6 乗算 ＋ 18 FMA ＋ 4 乗算 ＋ 12 FMA ≒ 40 演算。 素朴に 21 個の j[p]*j[q] を double で回すと 72 演算になるうえ、 k++ を伴う二重ループはベクトル化されない（実測で 2.4〜2.8 倍遅い）。

5.2 並列化と縮約

class GNBody : public ParallelLoopBody {
    void operator()(const Range& r) const CV_OVERRIDE {
        GNSums s;
        gnRows(gx_, gy_, X_, Y_, im_, tm_, r.start, r.end, s);  // 行ストライプ

スレッド間で共有するのは 30 個の double だけなので、縮約は事実上ただである。 これが効くのは Mat::dot が並列化されていないためで、 この段は現状 12 コアのうち 1 コアしか使っていない。

OpenCV 4.1.0 の gemm は P×N と N×P のような極端に縦長／横長のケースに最適化されていない。 [G;i‾; t‾] を積んで AAT 一発で全部出す案 （数学的には最も美しい）も同様に遅かった。

7.2 素朴な融合は単スレッドで遅い

j[6] を作って 21 個の j[p]*j[q] を double で二重ループする実装は、 現状より 2.3〜1.8 倍遅い。因数分解して straight-line にすることが本質で、 「融合すれば速い」わけではない。

8. 残っている余地と制約

  • 座標 x, y は読む必要がない。 それぞれ列番号・行番号なのでその場で生成できる。6 面 → 4 面になり、 さらに 3 割ほど流量が減るはず（未実装・未計測）。
  • SIMD 明示。現在はコンパイラの自動ベクトル化に任せている。30 個のアキュムレータは YMM レジスタ 16 本に収まらないので L1 に溢れている。ブロック分割すれば改善余地がある。
  • homography は実装済み。最も効いた。初版はここで「画素ごとの除算が入るので そのままでは面分割積の形にならない」と書いたが、これは誤りだった。除算は勾配側に畳み込めばよく （§4.3）、OpenCV 自身の image_jacobian_homo_ECC が既にその形になっている。 P = 8 は最も伸びしろが大きく、実測でも窓 768・4 スレッドで 2.47×（全 4 種別の最高値）。
  • translation / euclidean も実装済みだが利得は小さい。 w=(1) なので ヘッセが 3 / 6 成分しかなく、この段の比重が小さい。窓 768・4 スレッドで 1.27× / 1.88×。 それでも euclidean が affine（2.00×）に近いのは、 gr の生成が 1 パスに畳まれるため。
  • 上流提出は最適化 1 から。§3 の一次結合は 3 行で、レイアウトにもアルゴリズムにも 触れず、すべての動作種別に効く。§4〜5 は新しいカーネルを持ち込むので別件にすべきである。

9. まとめ

  1. 更新の射影は数式から消える。 GT(λ t‾− i‾)= λvt− vi。 3 行の置き換えで 15 面が浮く。
  2. 四つの運動種別すべてでヤコビアンは面分割積の列部分集合。 translation / euclidean / affine / homography の違いは u, w の中身と取り出す列だけで、 累積するスカラは常に tri(K)·tri(L)。 affine ではそれが 21 ではなく 18 になる。 H=∑n (gngnT) ⊗ (cncnT) という形から直ちに従う。
  3. ヤコビアンを実体化しなければ、1 反復の 85 面が 6 面になる。 30 個のスカラを 1 パスで累積すれば済む。
  4. この段は現状 1 コアしか使っていない（Mat::dot に parallel_for_ が無い）。 行ストライプ並列は縮約が 30 スカラなので事実上ただ。
  5. 節約は P とともに増える。ヤコビアンを実体化しない利得は 1 パスで済むことなので、パラメータが多いほど得をする。窓 768・4 スレッドで translation 1.27× / euclidean 1.88× / affine 2.00× / homography 2.47×。 初版が「homography は面分割積にならないので未実装」と書いたのは誤りで、 実際には最も効く相手だった。
  6. warp 削減と組み合わせると穴が無くなる。warp 削減は小窓（256 で 1.26〜1.52×）、 融合 GN は大窓で効くので、両方入れると 4 スレッドで 窓・運動種別によらず 1.40〜2.89×。この段だけを取り出せば最大 6.3×。 精度・バイアス・収束半径はいずれも数値的に不変。
