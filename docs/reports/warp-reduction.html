Reducing the warps per ECC iteration

How three bilinear warps per iteration become one, and why it is allowed
Baseline: OpenCV cv::findTransformECC (forward-additive ECC)  /  this fork: src/fast_ecc.cpp

1. Summary

The change

3 → 1

Geometric warps per iteration (warpAffine / warpPerspective). The gradients are obtained by running filter2D on the warped image instead.

Why it is cheaper

warp ≫ conv

A bilinear warp costs a coordinate transform plus a four-tap interpolation per pixel, and warpPerspective adds a division. A 1×3 convolution and an addWeighted cost a handful of multiply-adds.

Why it is correct

A⁻ᵀ

The chain-rule factor is undone with one addWeighted. Exact for translation, euclidean and affine; an approximation only for homography.

ECC iteratively maximises ρ(p)=⟨îr, iw(p)⟩ / ‖iw(p)‖. Each iteration needs two things: (a) the warped image iw, and (b) the gradient ∇I(W(x)) that the parameter Jacobian is built from. The whole speed-up comes from changing how (b) is obtained.

2. What changed

2.1 OpenCV — warp the gradients every iteration

The gradient ∇I of the input is computed once before the loop, and then four images are warped every iteration — the image, both gradients, and the mask. Three of those are bilinear warps of image data.

// before the loop: one gradient pass over the whole input
filter2D(imageFloat, gradientX, -1, dx);
filter2D(imageFloat, gradientY, -1, dx.t());

// every iteration: three geometric warps
warpAffine(imageFloat, imageWarped,     map, ...);  // the image
warpAffine(gradientX,  gradientXWarped, map, ...);  // gradient x  <- expensive
warpAffine(gradientY,  gradientYWarped, map, ...);  // gradient y  <- expensive
warpAffine(preMask,    imageMask,       map, ...);  // the mask (nearest neighbour)

2.2 This fork — warp only the image, then differentiate it

Only the image and the mask are warped. The gradients are produced by differentiating the already warped image with filter2D, then undoing the chain-rule factor with addWeighted.

// every iteration: one geometric warp of image data
warpAffine(imageFloat, imageWarped, map, ...);          // the image, and only the image
warpAffine(preMask,    imageMask,   map, ...);            // the mask

// gradients taken on the warped image (cheap)
filter2D(imageWarped, imageWarpedGradientX, -1, dx);     // separable 1x3
filter2D(imageWarped, imageWarpedGradientY, -1, dx.t());

// undo the chain-rule factor, per pixel (cheap)
warp_gradients_affine_ECC(imageWarpedGradientX, imageWarpedGradientY,
                          map, gradientXWarped, gradientYWarped);
//  which is: addWeighted(gx,  d/det, gy, -c/det, 0, outX);
//            addWeighted(gx, -b/det, gy,  a/det, 0, outY);

The pre-loop gradient pass is gone entirely — there is nothing left to warp, so there is nothing to precompute.

A bilinear warpAffine does an inverse coordinate transform, a four-tap interpolation and a bounds check for every pixel. warpPerspective adds a division per pixel on top. A 1×3 filter2D and an addWeighted are a few multiply-adds each. Replacing two heavy warps with four light passes is worth most where the warp is most expensive, which is homography.

Geometric warps of image data, per iteration (fewer is faster)

What is removed is the most expensive operation in the loop. For homography, two divisions-per-pixel warpPerspective calls disappear.

The gain is not uniform, and a single ratio for it would be misleading. It is largest at small windows and on a single thread, and decays to break-even at large windows with a thread pool — OpenCV parallelises the warpAffine being removed above roughly 384 px, but not the filter2D and addWeighted that replace it. That is measured in the companion report.

4. Why it is allowed

The warped image is iw(x) = I(A·x + t), where A is the 2×2 linear part of the map (WARP_INVERSE_MAP convention). Differentiating that with filter2D brings down a Jacobian factor by the chain rule:

∂x[ I(A·x + t) ] = Aᵀ · ∇I(W(x)) (so filter2D returns g̃ = Aᵀ ∇I, not ∇I)

What the ECC Jacobian assembly needs is the bare ∇I(W(x)). So warp_gradients_*_ECC multiplies by A⁻ᵀ — a single addWeighted per output channel — and recovers it exactly: A⁻ᵀ g̃ = A⁻ᵀAᵀ ∇I = ∇I.

The frame change is a plain 2×2 matrix and inverting it recovers ∇I exactly. For an orthonormal A the inverse transpose is A itself, which is why those two cases can use the linear part directly.

homography

approximate

A projective warp has a Jacobian that varies per pixel; only its linear part is used here. The residual factor is symmetric positive definite, so it acts as a preconditioner — the ascent direction is preserved and the fixed point where the step goes to zero is unchanged.

The recombination coefficient does not move the fixed point. It is an invertible reparameterisation of the step, so Jᵀr = 0 is the same condition either way. This fork originally multiplied by A rather than A⁻ᵀ; correcting it was a matter of saying the right thing in the code, not a measurable accuracy gain — corner RMS moved by less than 0.001 px over 180 random trials, with no systematic difference.

5. What the change drags along with it

5.1 Differentiating after the warp contaminates the border

Running filter2D on the warped image reads across the boundary between the valid region and the zero fill, so the gradients there are wrong. OpenCV does not have this problem, because it warps gradients that were computed on the untouched input. So this fork zeroes a two-pixel rim of the mask and throws those gradients away. It is not an optimisation — it is the correction that the optimisation makes necessary.

preMask.row(0..1).setTo(0);  preMask.row(rows-2..rows-1).setTo(0);   // invalidate a 2 px rim
imageWarpedGradientX.setTo(0, 1 - imageMask);                        // discard those gradients

5.2 A separate border defect, inherited rather than introduced

There is a second, unrelated border problem that this fork carried over from ecc.cpp verbatim: the Gaussian pre-filter extrapolates the template border with BORDER_REFLECT_101, fabricating a ring gaussFiltSize/2 px wide that was then used at full weight. It biases the estimated scale downward. It is reported and fixed upstream, and fixed here.

The two are easy to confuse and are not the same thing. The rim above exists because gradients are taken after the warp; the ring exists because a blur invents data at the edge, and it is there whether or not the warp reduction is applied.

6. Conclusion

The speed-up is one substitution: instead of obtaining each iteration's gradients by warping ∇I, obtain them by differentiating the warped image and undoing the chain-rule factor with an addWeighted. That takes the geometric warps of image data from 3 to 1 per iteration.

  • Exact for translation, euclidean and affine. For homography it is an approximation that acts as a positive-definite preconditioner, so convergence is preserved.
  • Worth most for homography, where warpPerspective carries a per-pixel division.
  • Comes with an obligation: the two-pixel rim mask that discards gradients contaminated by differentiating across the fill boundary.
  • The measured gain depends on window size and thread count — see the companion report before quoting a number.
